# Сайт "Build Roulette" для Юры — принятые решения

Документ фиксирует архитектурные решения, принятые в обсуждении, и причины, по которым они были выбраны.
Обновляется по мере появления новых решений — не переписывается с нуля.

## Идея

Упрощённый аналог [PoE Roulette](https://poeroulette.com/) (build-roulette) под конкретный сценарий "приватной лиги" стримера:
у стримера есть один публичный Google-документ (Sheet), в котором несколько списков —
ники игроков, восхождения (Ascendancies), скиллы (включая трансфигурированные варианты).
Сайт должен уметь забрать эти списки, дать нажать кнопку "крутить" и выдать результат.

## 1. Источник данных — публичный Google Sheet

Данные читаются из **публичного** Google Sheet (доступ "Anyone with the link can view").
Экспорт в CSV работает без авторизации через ссылку вида:

```
https://docs.google.com/spreadsheets/d/{ID}/export?format=csv&gid={GID}
```

Проверено вживую (2026-09-20): серверный запрос (без браузера, без логина) успешно получает
CSV-содержимое реального публичного Sheet стримера.

## 2. Проблема: CORS блокирует прямой fetch из браузера

Статичный сайт на GitHub Pages (`*.github.io`) состоит только из статичных файлов — там нет
своего сервера, который мог бы сходить в Google от своего имени.

Проверено вживую (2026-09-20): `fetch()` к экспорт-ссылке Google Sheets прямо со страницы,
открытой на реальном `*.github.io` домене, падает с `TypeError: Failed to fetch` —
это браузерная блокировка CORS (Google не присылает `Access-Control-Allow-Origin` для
произвольных сторонних доменов на этом эндпоинте). При этом тот же URL сервером отдаётся
нормально — то есть проблема не в правах доступа и не в сети, а именно в браузерном
ограничении.

Также проверен обходной путь через JSONP (`<script>`-тег, не подчиняется CORS) —
`gviz/tq?tqx=out:json`. Google официально поддерживает такой формат, но в тесте эндпоинт
ответил `503` — решение существует, но ненадёжно/недокументировано официально, полагаться
на него для рабочего инструмента не стоит.

## 3. Принятое решение: синхронизация через GitHub Actions по расписанию

Вместо live-запроса из браузера — **GitHub Action по cron-расписанию, раз в 3 минуты**,
которая на стороне GitHub (не в браузере пользователя) скачивает CSV из Google Sheet и
коммитит его как статичный файл в тот же репозиторий. Сайт читает уже свой собственный файл
(тот же домен → CORS не действует).

Плюсы:
- Не нужен отдельный бэкенд/прокси-сервис.
- Полностью укладывается в бесплатный GitHub Pages + GitHub Actions.
- Достаточная свежесть данных для рулетки (не нужен real-time).

Минус: обновление не мгновенное, задержка до 3 минут после правки Google Sheet.

### Стоимость / лимиты GitHub Actions (проверено 2026-09-20)

Репозиторий для GitHub Pages на бесплатном тарифе обязан быть **публичным** — а для
публичных репозиториев GitHub Actions на стандартных hosted-раннерах **бесплатен и без
ограничения по минутам**. Лимиты по минутам (2000/3000/50000 в месяц) действуют только
для **приватных** репозиториев — нас это не касается.

Рекомендация: не делать cron чаще, чем раз в несколько минут — из-за неофициальных
анти-абьюз ограничений GitHub на слишком частые cron-джобы в публичных репозиториях.
Раз в 3 минуты — в безопасных пределах.

### Наблюдение: первый запуск по расписанию у GitHub может сильно задерживаться

Проверено вживую (2026-09-20): после создания `sync-sheet.yml` с `cron: "*/3 * * * *"`
воркфлоу не сработал сам ни разу за ~3 часа (это ~60 упущенных тиков) — только два ручных
запуска через `workflow_dispatch`. Конфиг при этом корректен (воркфлоу в статусе `active`,
права Actions `enabled: true, allowed_actions: all`, ветка по умолчанию — та же `master`,
куда пушим) — ручной запуск отрабатывает мгновенно и успешно подтягивает свежие данные.

Это не баг проекта, а известная особенность планировщика GitHub Actions: первое срабатывание
только что созданного `schedule`-триггера может задержаться на час и более (в отличие от
задержек внутри уже "разогретого" расписания, которые обычно не превышают нескольких минут).
Если через несколько часов после создания воркфлоу расписание так и не начнёт тикать само —
следующий шаг для диагностики: тривиальный коммит в сам файл `sync-sheet.yml` (иногда
заставляет GitHub перерегистрировать cron) или ручной запуск через `workflow_dispatch` как
временный обход, пока не разберёмся.

## 4. Запись результата — без Google API, выгрузка CSV

Запись обратно в Google Sheet требует Google Sheets API с OAuth-разрешением от владельца
документа на конкретный файл (публичность на чтение ≠ доступ на запись) — это отдельный
Google Cloud проект, OAuth consent screen и т.д. Для упрощённой версии этого решили избежать.

**Принято**: по завершении рулетки сайт отдаёт стримеру **полный CSV-файл на скачивание**
с результатом розыгрыша. Дальнейшая judgement-call (вставить вручную в тот же Google Sheet,
переслать игрокам и т.п.) — на усмотрение стримера, вне зоны ответственности сайта.

## 5. Превью персонажей — шарики вместо анимированных человечков

Изначально рассматривался вариант с анимированными 2D-человечками (спрайтовая анимация,
смена голого/одетого состояния, спам скилла) — по аналогии с тем, как это делалось бы в
Unity через Animator и слои спрайтов. В вебе прямой аналог — layered sprite animation на
Canvas (например, PixiJS): отдельные спрайтшиты для тела, одежды под восхождение и
VFX скилла, синхронизированные по кадрам. Признано избыточным объёмом работы для этого
проекта.

**Принято**: вместо человечков — простые шарики/круги с лёгкой поведенческой анимацией:
- Состояние "А" (до присвоения восхождения/скилла) — шарик просто катится (вращение +
  перемещение), на нём/рядом только ник.
- Состояние "Б" (после того как рулетка присвоила восхождение и скилл) — шарик подпрыгивает,
  на нём отображаются иконки восхождения и скилла.

Реализуется чистым CSS/JS (transform: translate/rotate для качения, translateY для прыжка) —
без спрайтшитов и без Canvas, что кардинально проще в разработке.

## 6. UI/UX рулетки

### Общая раскладка экрана

Две зоны на экране:
- **Таблица игроков** — список ников, у каждого игрока строка; после розыгрыша в строке
  появляется выданное восхождение и скилл. Текущая (активная/выбранная) строка подсвечена.
- **Зона превью "толпы"** — шарики из раздела 5, часть экрана с превью всех игроков.

### Управление и лимиты рероллов

- Одна большая кнопка **"КРУТИТЬ БАРАБАН"** — основной розыгрыш.
- Две маленькие кнопки под ней: **"крутить восхождение"** и **"крутить скилл"** — отдельные
  рероллы только одной из двух частей комбинации.
- Лимит рероллов на игрока: **1 бесплатный реролл** + **1 дополнительный** после проверки
  видео с убийством любого босса на приватке (условие проверяется вручную стримером/модератором,
  не автоматически сайтом).

### Механика самого розыгрыша (попап)

По нажатию кнопки открывается попап в стиле казино-слота:
- Внутри — "барабаны", крутящиеся сверху вниз, на них иконки + текст восхождений и отдельно
  иконки + текст скиллов (как в слот-машине с несколькими колонками).
- После остановки — выданная комбинация подсвечивается снизу попапа, проигрывается
  "фанфарная" анимация/звук.
- Появляется кнопка **"закрыть"**.
- После закрытия: в таблице слева появляется запись о выданном восхождении и скилле для
  этого игрока; соответствующий шарик в зоне превью (сматченный по нику) переезжает в
  состояние "Б" — перемещается в нижнюю часть зоны превью, начинает "шевелиться" активнее,
  на нём появляются иконки восхождения и скилла.

Референс механики розыгрыша — [PoE Roulette](https://poeroulette.com/), у него уже реализован
похожий слот-попап.

### Источник иконок восхождений/скиллов

**Принято**: иконки восхождений и скиллов брать напрямую из майненных файлов Path of Exile
(датамайн-ассеты игры). Обосновано тем, что проект некоммерческий (приватная лига стримера,
без монетизации), а сам PoE Roulette как референс, судя по всему, делает так же.

- **Колонка Б** — список восхождений, короче колонки А (19 значений, строки 2–20):

  Hierophant, Guardian, Necromancer, Occultist, Elementalist, Assassin, Saboteur, Trickster,

Важно: **трансфигурированных вариантов скиллов в списке нет** — только базовые названия

(раздел 6). При парсинге нужно учитывать, что колонки разной длины (пустые ячейки в конце
колонки Б — норма, не ошибка данных).

## 8. Формат итогового CSV с результатом розыгрыша

**Принято**: итоговый CSV повторяет структуру вкладки "участники" (раздел 7), но только
подмножеством колонок, относящихся к результату розыгрыша: `Логин, Подкласс, Умение,
Выдан слот, Был реролл`. Служебные/непричастные к розыгрышу колонки исходной вкладки
(`#`, `Логин совпадает`, колонки под боссов) в выгрузку не включаются — по ним стример
и так ведёт учёт сам, прямо в Google Sheet.

### Реализация (2026-09-20)

Кнопка «Скачать результат (CSV)» под таблицей участников (`exportResultsCsv` в `js/app.js`)
собирает пять колонок из уже загруженного в память состояния `participants` (не делает
повторный запрос к Google Sheet) и отдаёт файл через `Blob` + временный `<a download>` —
без серверной части, чистый браузерный API. Поле `Выдан слот` раньше нигде не читалось из
CSV участников (`data/participants.csv`), для выгрузки добавлено в `loadParticipants`.

В начало файла добавлен BOM (`﻿`) — без него Excel при открытии CSV с кириллицей в
UTF-8 иногда угадывает не ту кодировку и показывает "кракозябры"; с BOM открывается
корректно сразу. Сериализация полей (`stringifyCsv`/`csvEscapeField` в `js/csv.js`) экранирует
поле в кавычки только если внутри запятая/кавычка/перенос строки — общий формат CSV, не
специфичный для этого проекта.

## 9. Источник датамайн-иконок — poedb.tw

Проверено вживую (2026-09-20). Источник — **poedb.tw**, комьюнити-датабейс Path of Exile,
раздающий смайненные ассеты игры через собственный CDN `cdn.poedb.tw` (формат `.webp`).

### Скиллы

Страница `https://poedb.tw/us/Skill_Gems` содержит **все 563 скилл-гемма на одной странице**
сразу с иконками — не нужно ходить на страницу каждого гемма отдельно. Структура (проверено
по сырому HTML): для каждого гемма рядом стоят
`<img src="https://cdn.poedb.tw/image/Art/2DItems/Gems/{InternalCodeName}.webp">` и
`<a href="/us/{Name_With_Underscores}">{Display Name}</a>` — то есть отображаемое имя гемма
и URL его иконки идут в одном блоке разметки, легко достать одним парсингом за один запрос.
Внутреннее кодовое имя файла (`{InternalCodeName}`) не совпадает с отображаемым именем
(например, у "Artillery Ballista" иконка называется `MortarTotemSkillIcon.webp`) — то есть
URL нельзя просто вычислить по названию скилла, нужен именно парсинг этой сводной страницы.

### Восхождения

У каждого из 19 восхождений — отдельная страница (`https://poedb.tw/us/{Name}`, например
`.../Slayer`, `.../Necromancer`), на которой есть основная иконка класса вида
`https://cdn.poedb.tw/image/Art/2DArt/UIImages/Common/Icon{АтрибутнаяПара}_{Name}.webp`
(например `IconStrDex_Slayer.webp`, `IconInt_Necromancer.webp`). Атрибутный префикс не
предсказать по названию восхождения без сверки с базовым классом — но восхождений всего 19,
поэтому дешевле просто разово сходить на каждую из 19 страниц, чем городить таблицу
соответствий атрибутов.

### Принятое решение по хранению

**Пересмотрено**: иконки **хотлинкаются напрямую с `cdn.poedb.tw`** в `<img src="...">`,
без скачивания и без переразмещения файлов в своём репозитории. Причины смены решения
(изначально предлагалось скачивать и коммитить локально, см. историю раздела):
- Проще в разработке и поддержке — не нужен отдельный шаг скачивания/коммита ассетов при
  каждом обновлении списка скиллов/восхождений.
- Авторские права — иконки являются датамайн-ассетами игры GGG; прямая ссылка на сторонний
  CDN (просмотр чужого изображения по ссылке) не создаёт копию на своей стороне, в отличие
  от скачивания и переразмещения файлов у себя.

Сайт в рантайме зависит от доступности `cdn.poedb.tw` — это признано некритичным: poedb —
такой же основной общепризнанный community-датабейс по Path of Exile, как и poe.ninja,
а не второстепенный ресурс, рисков по надёжности/доступности не закладываем.

### Уточнение: иконки скиллов — с официального CDN GGG, не с poedb

Проверено вживую (2026-09-20): у Grinding Gear Games есть собственный официальный CDN
`web.poecdn.com`, и иконки геммов на нём лежат по **тому же относительному пути**, что и
на зеркале poedb, только с расширением `.png` вместо `.webp`:

```
https://web.poecdn.com/image/Art/2DItems/Gems/{InternalCodeName}.png
```

Подтверждено на нескольких примерах, включая гемм со сложным внутренним именем
(`Artillery Ballista` → `MortarTotemBowSkillGem.png`). То есть workflow не меняется —
по-прежнему нужен скрейп `poedb.tw/us/Skill_Gems` для получения пары "отображаемое имя
скилла → InternalCodeName", но итоговая ссылка в JSON-таблице должна указывать на
`web.poecdn.com` (официальный первоисточник), а не на `cdn.poedb.tw` (чужое зеркало).

Для иконок **восхождений** такой же официальный путь на `web.poecdn.com` пока не найден
(путь `Art/2DArt/UIImages/Common/Icon{Attr}_{Name}` с официального CDN отдаёт 404) — для них
пока оставляем ссылки на зеркало `cdn.poedb.tw` как и раньше. Если позже найдётся официальный
путь и для восхождений — обновить аналогично.

### Итог: `data/icons.json` собран

Готова статичная таблица `{ skills: {имя → URL}, ascendancies: {имя → URL} }` под все имена
из вкладки "Умения и классы" (раздел 7) — без какого-либо скрейпера в составе сайта или
CI: файл собран один раз и закоммичен как обычные данные, как и договаривались.

- **Скиллы**: 158 из 160 — ссылки на `web.poecdn.com` (официальный CDN). Не нашлись:
  `Dark Pact`, `Magma Orb` — на сводной странице poedb их вообще нет (возможно, устаревшие/
  переработанные версии скиллов), для них в JSON стоит `null`.
- **Восхождения**: 18 из 19 — ссылки на `cdn.poedb.tw` (путь `UIImages/Common`, начиная с
  `Icon{АтрибутнаяПара}_{Имя}.webp`; для Scion — общий `IconStrDexInt.webp`, у неё нет
  отдельной ascendancy-иконки). Не нашлась: `Raider` — у самого poedb на страницу класса
  Ranger ссылка на "Raider" ведёт на не относящуюся к делу страницу ("Raider (Ascendant
  passive)", это другой игровой объект с тем же именем) — `null` в JSON.

Важное наблюдение по надёжности `cdn.poedb.tw`: при тестировании (много быстрых
последовательных запросов подряд) сайт за Cloudflare начал отдавать **403** на прямые
запросы без Referer, хотя сами файлы существуют и в норме отдаются с кодом 200 — похоже
на защиту от ботов/скрейпинга, а не на постоянное ограничение по Referer. Для обычного
браузерного трафика с реальной страницы риск ниже, чем у моих повторных автоматизированных
запросов, но стоит иметь в виду как потенциальный источник изредка "не прогрузившихся"
иконок восхождений в проде.

Три нерешённых позиции (`Dark Pact`, `Magma Orb`, `Raider`) — на усмотрение донабрать
вручную позже (например, через poewiki.net как альтернативный источник) либо оставить как
есть: сайт должен уметь показать плейсхолдер, если URL иконки — `null`.

### Пересмотрено ещё раз: восхождения тоже переехали на официальный CDN (спрайт-атлас)

При реальном тестировании в браузере (не в curl) `cdn.poedb.tw` стабильно отдавал 403/503
на все иконки восхождений сразу у нескольких игроков одновременно — риск из раздела выше
подтвердился на практике, а не только в теории.

Решение нашлось через сырые данные официальной страницы дерева пассивок
(`pathofexile.com/passive-skill-tree`, встроенный в HTML объект `passiveSkillTreeData`):
GGG раздаёт иконки восхождений не поштучно, а через **спрайт-атлас**
`https://web.poecdn.com/image/passive-skill/ascendancy-4.webp?22bd887d` (3480×3480,
официальный CDN, `Access-Control-Allow-Origin: *`, проверено вживую — 200 OK) с блоком
`coords`, где под ключами вида `ClassesSlayer`, `ClassesNecromancer` и т.д. лежат пиксельные
`{x, y, w, h}` (650×650, у части — 765×765) каждой иконки внутри атласа. Там же нашлись и
ранее пропавшие `Raider`, а Scion — под ключом `ClassesAscendant` (её ascendancy-класс в игре
официально называется "Ascendant").

**Принято**: `data/icons.json.ascendancies` теперь хранит не прямую ссылку на файл, а
дескриптор кропа `{ sheet, sheetW, sheetH, x, y, w, h }`; на сайте иконка восхождения — это
`<div>` с `background-image` на атлас и вычисленными `background-position`/`background-size`
(классическая CSS-спрайт-техника), а не `<img src>`. Скиллы (`data/icons.json.skills`)
не тронуты — они как и раньше обычные ссылки на `web.poecdn.com/.../Gems/{Code}.png`,
там проблем не было. Все 19 восхождений теперь официальные и рабочие, тема иконок
восхождений закрыта.

По-прежнему нужен: один разовый (или периодический, при обновлении справочника скиллов/
восхождений) скрейп `poedb.tw` — не для скачивания файлов, а для построения и обновления
JSON-таблицы соответствия "название скилла/восхождения → URL иконки на `cdn.poedb.tw`",
которая коммитится в репозиторий как обычные текстовые данные (не изображения).

### Финальный пересмотр: отказ от poecdn/CDN, извлечение прямо из клиента игры

Пользователь сходил в дискорд-канал `tooldev-general` (комьюнити разработчиков тулов под PoE)
и получил чёткую рекомендацию: **не использовать poecdn (ни `web.poecdn.com`, ни `cdn.poedb.tw`)
в своих тулзах вообще** — ни хотлинком, ни как источник для скачивания. Правильный путь,
принятый в этом тулдев-комьюнити — извлекать арт прямо из установленного клиента/патч-файлов
игры через библиотеку
[`pathofexile-dat`](https://github.com/SnosMe/poe-dat-viewer/tree/master/lib) (npm-пакет,
CLI-инструмент) + ImageMagick для конвертации DDS → PNG. Это разовая операция (не встраивается
в сайт или CI) — то есть без какого-либо "скрейпера" в проекте, только конечные файлы в репо.

**Как это сделано (весь процесс — разовый, руками, 2026-09-20)**:

1. `npm install --global pathofexile-dat` + `winget install ImageMagick.ImageMagick`.
2. `pathofexile-dat` умеет скачивать нужные файлы прямо с официальных патч-серверов GGG по
   номеру патча (`"patch": "3.29.3.3"`, актуальная версия берётся с
   `raw.githubusercontent.com/poe-tool-dev/latest-patch-version/main/latest.txt`) — то есть
   тоже официальный источник, но не тот самый "poecdn для картинок", от которого просили
   отказаться (это патч-CDN для скачивания игры, легитимный для этого инструмента путь).
3. Слепые догадки по путям файлов не работают — нужны точные пути. Их дают официальные
   dat-таблицы схемы (`github.com/poe-tool-dev/dat-schema`):
   - `ActiveSkills.Icon_DDSFile` — путь к **чистому арту скилла** (без "клетки" с цветным
     геммом — то, что мы изначально и хотели, см. историю раздела).
   - `Ascendancy.PassiveTreeImage` — путь к **полноразмерному иллюстрированному портрету**
     восхождения (реальный пример: `Art/2DArt/BaseClassIllustrations/SlayerAscendency.dds`,
     оригинал 3100×1856 — сюжетный арт персонажа, а не маленькая иконка-медальон).
   - Обе таблицы выгружаются через `config.json` → `"tables": [...]` в `pathofexile-dat`.
4. По `DisplayedName` из `ActiveSkills` сопоставили все 160 названий скиллов из справочника
   (раздел 7) — 158 нашлись, `Dark Pact` и `Magma Orb` подтверждены отсутствующими и в
   актуальном клиенте (устаревшие/убранные скиллы, не только на poedb) — остаются `null`.
   `Sweep` сопоставлен вручную на `Holy Sweep` (переименован в игре).
5. По `Id` из `Ascendancy` выгружены портреты всех 18 классических восхождений одним заходом.
   Для Scion (`Id: "Ascendant"`, `PassiveTreeImage` пустой, а сам `pathofexile-dat` падает
   с ошибкой на её `BackgroundImage`-пути — баг инструмента на этом конкретном ассете) —
   не стали фиксить инструмент ради одной иконки, а разово скачали и обрезали локально уже
   найденный ранее кроп `ClassesAscendant` с официального атласа `ascendancy-4.webp`
   (легитимный источник тот же GGG, просто вручную, не хотлинком).
6. Портреты восхождений (по ~5 МБ каждый в оригинале, 86 МБ на все 18) прогнаны через
   ImageMagick: `-resize "480x480>" -quality 85`, PNG → JPEG — итог 0.35 МБ на все 19. Иконки
   скиллов (64×64 PNG) уже маленькие, не сжимались (1 МБ на 158 штук).

**Итог**: `data/icons.json` теперь хранит **относительные локальные пути** (`img/skills/*.png`,
`img/ascendancies/*.jpg`) вместо любых внешних URL — сайт ни при каких обстоятельствах не
делает живых запросов к сторонним CDN за иконками. Файлы лежат прямо в репозитории
(`img/skills/`, `img/ascendancies/`). Код на сайте (`js/roulette.js`) радикально упростился —
оба типа иконок теперь просто `<img src="...">`, вся логика обрезки спрайтов/геммов из
предыдущих итераций (раздел выше) удалена за ненадобностью — извлечённые файлы уже содержат
ровно то, что нужно показать, без лишних полей/геммов/кропа.

Не хватает: `Dark Pact`, `Magma Orb` (скиллы, реально отсутствуют в текущей версии игры —
`null` в JSON, сайт показывает плейсхолдер). Восхождения — все 19 закрыты.

## 10. Поведение зоны превью — референс "песочные часы"

**Принято**: зона превью "толпы" (раздел 5/6) — это чёрная область, разделённая по аналогии с
песочными часами на верхнюю и нижнюю часть:
- **Верх** — шарики игроков, которым ещё не присвоено восхождение/скилл (состояние "А"),
  слегка покачиваются на месте, как песчинки в верхней колбе до высыпания.
- Когда игроку выпадает комбинация — его шарик **перемещается сверху вниз** (по аналогии с
  падением песчинки через горлышко часов) и оказывается в нижней части зоны.
- **Низ** — шарики уже разыгранных игроков (состояние "Б"), там движение **чуть активнее**,
  чем в верхней части (не просто лёгкое покачивание) — на них уже отображаются иконки
  восхождения и скилла.

Открытых вопросов по общей архитектуре и UX на данный момент не осталось — все пункты
из предыдущей версии списка закрыты (разделы 1–10).

### Реализация (2026-09-20)

Зона превью — один `<div id="crowd-preview">` фиксированной высоты, без вложенных
контейнеров под верх/низ: разделительная линия на середине высоты нарисована псевдоэлементом
`::after`, а каждый шарик (`.crowd-ball`) позиционируется абсолютно через инлайновые `top`/`left`
(в px), которые и определяют, в какой из половин он находится.

Состояние "А" (`decisions.md`, раздел 5) — CSS-анимация `crowd-idle` на внутреннем элементе
шарика (translateX + rotate по кругу, имитация качения на месте). Переход в состояние "Б"
при завершении **первого** розыгрыша (`mode: "full"` в `handleRoll`, `js/app.js`) — смена
инлайнового `top` на случайное значение в нижней половине с CSS `transition`, класс
`crowd-ball--active` переключает анимацию на `crowd-active` (более резкие прыжки) и в шарик
добавляются иконки восхождения/скилла (те же файлы из `data/icons.json`, что и в барабанах
попапа). Реролл одной из частей (`mode: "ascendancy"`/`"skill"`) шарик **не двигает** —
только перерисовывает иконки на месте (не должен "падать" повторно, он уже в нижней зоне).
Шарик находится по нику через `data-login` + `CSS.escape` (ники не гарантированно ASCII/без
спецсимволов, поэтому escape обязателен, не голая интерполяция в селектор).

### Доработка: расстановка шариков без наложений (2026-09-20)

Первая версия ставила шарики чисто случайно по всей ширине зоны — при 50 участниках в
узкой верхней половине они массово перекрывали друг друга, ники было не разобрать.
Пользователь попросил "легко растолкать" их, чтобы каждый был виден, и вдвое снизить
скорость вращения в состоянии "А" (жаловался, что шарики "наезжают" друг на друга).

**Принято**: вместо полноценной физической симуляции — упрощённая эвристика (`findCrowdSpot`
в `js/app.js`): для каждого нового шарика перебирается до 80 случайных кандидатных точек
в границах своей зоны, из них выбирается та, что дальше всего от уже расставленных соседей;
если ни одна не проходит порог минимальной дистанции (диаметр шарика + запас), берётся
лучшая из перебранных — не идеально свободный от наложений результат, но однопроходный и
достаточно дешёвый при 50 участниках. Та же функция переиспользуется и при переезде шарика
в нижнюю зону после розыгрыша (сравнение идёт с текущими позициями уже разыгранных шариков,
считанными прямо из DOM через `parseFloat(style.left/top)`).

Чтобы 50 непересекающихся шариков вообще физически помещались в отведённой под них половине
зоны, дополнительно уменьшен диаметр шарика (56 → 44px) и увеличена общая высота
`#crowd-preview` (360 → 420px) — без этого даже идеальная раскладка не решила бы проблему,
места просто не было. Скорость анимации `crowd-idle` (качение в состоянии "А") снижена вдвое
(3s → 6s за цикл), как и попросил пользователь.

### Доработка: размер шариков, человечки-палочки, рандомизация вращения (2026-09-20)

Ещё один раунд правок по тому же экрану:
- **Шарики и текст увеличены на ~50%** (44 → 66px, шрифт ника 8 → 12px) — пользователь
  попросил улучшить читаемость. Чтобы вместить укрупнённые шарики, высота `#crowd-preview`
  выросла ещё раз (420 → 480px).
- **Человечки-палочки**: пользователь прислал руками пририсованную к скриншоту палку-человечка
  под шариком (`chelovek.png`, референс, не коммитился в репозиторий) и попросил показывать
  такую же после розыгрыша — комичный акцент. Реализовано как маленький inline-SVG
  (`.crowd-stick-figure`: круг-голова + линии тела/рук/ног, красный `stroke`) внутри
  `.crowd-ball-inner`, добавляется один раз при первом присвоении результата
  (`ensureCrowdStickFigure` в `js/app.js`) с CSS-анимацией "выскакивания" (`scale`+`opacity`).
  Так как это ещё один элемент под шариком, под него заложен запас высоты в нижней зоне
  (`CROWD_STICK_FIGURE_HEIGHT_PX`), иначе он обрезался бы границей `#crowd-preview`.
- **Вращение** в состоянии "А" снижено ещё вдвое (6s → 12s) и, что важнее, рандомизировано:
  раньше все шарики использовали одну и ту же CSS-анимацию с небольшим случайным
  `animation-delay` (0–2.5s при периоде 6s) — заметная часть шариков визуально крутилась
  синхронно. Теперь у каждого шарика своя случайная длительность (10–14s, инлайновый
  `animationDuration`) и **отрицательный** `animation-delay` в диапазоне своей же
  длительности — стандартный трюк, чтобы анимация сразу стартовала со случайной фазы цикла,
  а не "стояла" видимо неподвижной первые секунды до начала positive delay.
- **Кнопки рероллов переименованы** под точные названия колонок из Google Sheet: "крутить
  восхождение"/"крутить скилл" → "крутить подкласс"/"крутить умение" — тот же принцип, что и
  для заголовков таблицы (раздел 11), никаких "дружелюбных" синонимов.

### Счётчик рероллов — отдельная колонка "Количество рероллов", не переиспользуем "Был реролл"

В исходном (старом) документе стример кодировал число рероллов цветом текста в одной
ячейке `Был реролл`: пусто = 0, "Да" обычным цветом = 1, "Да" **красным** = 2. Экспорт в CSV
не сохраняет форматирование ячеек (цвет, жирность и т.п.) — только текстовое значение,
поэтому по CSV нельзя было отличить 1 от 2.

Первая попытка решения (хранить `0`/`1`/`2` текстом прямо в `Был реролл`) не подошла —
на эту колонку в Google Sheet уже настроена data-validation, ограничивающая значения до
`Да`/`Нет` (обнаружилось при повторном просмотре таблицы), число туда просто не влезет.

**Принято**: `Был реролл` остаётся как есть — `Да`/`Нет` (булево, по правилу валидации).
Число рероллов хранится в **отдельной новой колонке `Количество рероллов`** (добавлена
пользователем в Sheet вручную, без ограничений на значения). Сайт (`js/app.js`) читает
обе колонки: `Был реролл` — для поля `hadReroll` (отображается как есть), `Количество
рероллов` — парсится в `rerollsUsed`, стартовое состояние участника вместо жёсткого 0.
Названия колонок в таблице на сайте приведены в точное соответствие с названиями в
Google Sheet (`Логин`, `Подкласс`, `Умение`, `Был реролл`, `Количество рероллов`) — без
дружелюбных переименований вроде "Игрок"/"Скилл"/"Восхождение", по просьбе пользователя.
Значение `Количество рероллов` ≥ 2 подсвечивается в таблице красным и жирным — по аналогии
со старой цветовой схемой стримера, но как стиль текста, не цвет ячейки.

## 12. Фоновая музыка — YouTube IFrame API

Пользователь попросил фоновую музыку с YouTube (бесплатный трек по своей ссылке —
`youtube.com/watch?v=c2qofuQNV5w`).

**Принято**: без скачивания/переразмещения аудиофайла — встроен официальный
[YouTube IFrame Player API](https://developers.google.com/youtube/iframe_api_reference)
(`js/background-music.js`). Сам `<iframe>` (`#youtube-player`) в вёрстке присутствует, но
визуально скрыт (`position: fixed; left/top: -9999px` в `css/style.css`) — на странице виден
только квадратный toggle-кнопка «Музыка ВКЛ/ВЫКЛ» рядом с «КРУТИТЬ БАРАБАН» (расположение —
по прямой просьбе пользователя, не в отдельной шапке).

Важное ограничение, из-за которого автозапуска при загрузке страницы нет и не может быть:
современные браузеры блокируют автовоспроизведение видео/аудио со звуком без предварительного
клика пользователя по странице. Поэтому плеер (`YT.Player`) создаётся **лениво**, только при
первом клике по кнопке — это одновременно и обходит блокировку автоплея, и не грузит iframe API

YouTube IFrame API для зацикливания одиночного видео (обычный `loop: 1` без `playlist`
зацикливает только плейлисты).
