# Сайт "Build Roulette" для Юры — принятые решения

Документ фиксирует архитектурные решения, принятые в обсуждении, и причины, по которым они были выбраны.
Обновляется по мере появления новых решений — не переписывается с нуля.

## Идея

Упрощённый аналог [PoE Roulette](https://poeroulette.com/) (build-roulette) под конкретный сценарий "приватной лиги" стримера:
у стримера есть один публичный Google-документ (Sheet), в котором несколько списков —
ники игроков, восхождения (Ascendancies), скиллы (включая трансфигурированные варианты).
Сайт должен уметь забрать эти списки, дать нажать кнопку "крутить" и выдать результат.

## 1. Источник данных — публичный Google Sheet

Данные читаются из **публичного** Google Sheet (доступ "Anyone with the link can view").
Экспорт в CSV работает без авторизации через ссылку вида:

```
https://docs.google.com/spreadsheets/d/{ID}/export?format=csv&gid={GID}
```

Проверено вживую (2026-09-20): серверный запрос (без браузера, без логина) успешно получает
CSV-содержимое реального публичного Sheet стримера.

## 2. Проблема: CORS блокирует прямой fetch из браузера

Статичный сайт на GitHub Pages (`*.github.io`) состоит только из статичных файлов — там нет
своего сервера, который мог бы сходить в Google от своего имени.

Проверено вживую (2026-09-20): `fetch()` к экспорт-ссылке Google Sheets прямо со страницы,
открытой на реальном `*.github.io` домене, падает с `TypeError: Failed to fetch` —
это браузерная блокировка CORS (Google не присылает `Access-Control-Allow-Origin` для
произвольных сторонних доменов на этом эндпоинте). При этом тот же URL сервером отдаётся
нормально — то есть проблема не в правах доступа и не в сети, а именно в браузерном
ограничении.

Также проверен обходной путь через JSONP (`<script>`-тег, не подчиняется CORS) —
`gviz/tq?tqx=out:json`. Google официально поддерживает такой формат, но в тесте эндпоинт
ответил `503` — решение существует, но ненадёжно/недокументировано официально, полагаться
на него для рабочего инструмента не стоит.

## 3. Принятое решение: синхронизация через GitHub Actions по расписанию

Вместо live-запроса из браузера — **GitHub Action по cron-расписанию, раз в 3 минуты**,
которая на стороне GitHub (не в браузере пользователя) скачивает CSV из Google Sheet и
коммитит его как статичный файл в тот же репозиторий. Сайт читает уже свой собственный файл
(тот же домен → CORS не действует).

Плюсы:
- Не нужен отдельный бэкенд/прокси-сервис.
- Полностью укладывается в бесплатный GitHub Pages + GitHub Actions.
- Достаточная свежесть данных для рулетки (не нужен real-time).

Минус: обновление не мгновенное, задержка до 3 минут после правки Google Sheet.

### Стоимость / лимиты GitHub Actions (проверено 2026-09-20)

Репозиторий для GitHub Pages на бесплатном тарифе обязан быть **публичным** — а для
публичных репозиториев GitHub Actions на стандартных hosted-раннерах **бесплатен и без
ограничения по минутам**. Лимиты по минутам (2000/3000/50000 в месяц) действуют только
для **приватных** репозиториев — нас это не касается.

Рекомендация: не делать cron чаще, чем раз в несколько минут — из-за неофициальных
анти-абьюз ограничений GitHub на слишком частые cron-джобы в публичных репозиториях.
Раз в 3 минуты — в безопасных пределах.

## 4. Запись результата — без Google API, выгрузка CSV

Запись обратно в Google Sheet требует Google Sheets API с OAuth-разрешением от владельца
документа на конкретный файл (публичность на чтение ≠ доступ на запись) — это отдельный
Google Cloud проект, OAuth consent screen и т.д. Для упрощённой версии этого решили избежать.

**Принято**: по завершении рулетки сайт отдаёт стримеру **полный CSV-файл на скачивание**
с результатом розыгрыша. Дальнейшая judgement-call (вставить вручную в тот же Google Sheet,
переслать игрокам и т.п.) — на усмотрение стримера, вне зоны ответственности сайта.

## 5. Превью персонажей — шарики вместо анимированных человечков

Изначально рассматривался вариант с анимированными 2D-человечками (спрайтовая анимация,
смена голого/одетого состояния, спам скилла) — по аналогии с тем, как это делалось бы в
Unity через Animator и слои спрайтов. В вебе прямой аналог — layered sprite animation на
Canvas (например, PixiJS): отдельные спрайтшиты для тела, одежды под восхождение и
VFX скилла, синхронизированные по кадрам. Признано избыточным объёмом работы для этого
проекта.

**Принято**: вместо человечков — простые шарики/круги с лёгкой поведенческой анимацией:
- Состояние "А" (до присвоения восхождения/скилла) — шарик просто катится (вращение +
  перемещение), на нём/рядом только ник.
- Состояние "Б" (после того как рулетка присвоила восхождение и скилл) — шарик подпрыгивает,
  на нём отображаются иконки восхождения и скилла.

Реализуется чистым CSS/JS (transform: translate/rotate для качения, translateY для прыжка) —
без спрайтшитов и без Canvas, что кардинально проще в разработке.

## 6. UI/UX рулетки

### Общая раскладка экрана

Две зоны на экране:
- **Таблица игроков** — список ников, у каждого игрока строка; после розыгрыша в строке
  появляется выданное восхождение и скилл. Текущая (активная/выбранная) строка подсвечена.
- **Зона превью "толпы"** — шарики из раздела 5, часть экрана с превью всех игроков.

### Управление и лимиты рероллов

- Одна большая кнопка **"КРУТИТЬ БАРАБАН"** — основной розыгрыш.
- Две маленькие кнопки под ней: **"крутить восхождение"** и **"крутить скилл"** — отдельные
  рероллы только одной из двух частей комбинации.
- Лимит рероллов на игрока: **1 бесплатный реролл** + **1 дополнительный** после проверки
  видео с убийством любого босса на приватке (условие проверяется вручную стримером/модератором,
  не автоматически сайтом).

### Механика самого розыгрыша (попап)

По нажатию кнопки открывается попап в стиле казино-слота:
- Внутри — "барабаны", крутящиеся сверху вниз, на них иконки + текст восхождений и отдельно
  иконки + текст скиллов (как в слот-машине с несколькими колонками).
- После остановки — выданная комбинация подсвечивается снизу попапа, проигрывается
  "фанфарная" анимация/звук.
- Появляется кнопка **"закрыть"**.
- После закрытия: в таблице слева появляется запись о выданном восхождении и скилле для
  этого игрока; соответствующий шарик в зоне превью (сматченный по нику) переезжает в
  состояние "Б" — перемещается в нижнюю часть зоны превью, начинает "шевелиться" активнее,
  на нём появляются иконки восхождения и скилла.

Референс механики розыгрыша — [PoE Roulette](https://poeroulette.com/), у него уже реализован
похожий слот-попап.

### Источник иконок восхождений/скиллов

**Принято**: иконки восхождений и скиллов брать напрямую из майненных файлов Path of Exile
(датамайн-ассеты игры). Обосновано тем, что проект некоммерческий (приватная лига стримера,
без монетизации), а сам PoE Roulette как референс, судя по всему, делает так же.

колонки Б — норма, не ошибка данных).

## 8. Формат итогового CSV с результатом розыгрыша

**Принято**: итоговый CSV повторяет структуру вкладки "участники" (раздел 7), но только
подмножеством колонок, относящихся к результату розыгрыша: `Логин, Подкласс, Умение,
Выдан слот, Был реролл`. Служебные/непричастные к розыгрышу колонки исходной вкладки
(`#`, `Логин совпадает`, колонки под боссов) в выгрузку не включаются — по ним стример
и так ведёт учёт сам, прямо в Google Sheet.

## 9. Источник датамайн-иконок — poedb.tw

Проверено вживую (2026-09-20). Источник — **poedb.tw**, комьюнити-датабейс Path of Exile,
раздающий смайненные ассеты игры через собственный CDN `cdn.poedb.tw` (формат `.webp`).

### Скиллы

Страница `https://poedb.tw/us/Skill_Gems` содержит **все 563 скилл-гемма на одной странице**
сразу с иконками — не нужно ходить на страницу каждого гемма отдельно. Структура (проверено
по сырому HTML): для каждого гемма рядом стоят
`<img src="https://cdn.poedb.tw/image/Art/2DItems/Gems/{InternalCodeName}.webp">` и
`<a href="/us/{Name_With_Underscores}">{Display Name}</a>` — то есть отображаемое имя гемма
и URL его иконки идут в одном блоке разметки, легко достать одним парсингом за один запрос.
Внутреннее кодовое имя файла (`{InternalCodeName}`) не совпадает с отображаемым именем
(например, у "Artillery Ballista" иконка называется `MortarTotemSkillIcon.webp`) — то есть
URL нельзя просто вычислить по названию скилла, нужен именно парсинг этой сводной страницы.

### Восхождения

У каждого из 19 восхождений — отдельная страница (`https://poedb.tw/us/{Name}`, например
`.../Slayer`, `.../Necromancer`), на которой есть основная иконка класса вида
`https://cdn.poedb.tw/image/Art/2DArt/UIImages/Common/Icon{АтрибутнаяПара}_{Name}.webp`
(например `IconStrDex_Slayer.webp`, `IconInt_Necromancer.webp`). Атрибутный префикс не
предсказать по названию восхождения без сверки с базовым классом — но восхождений всего 19,
поэтому дешевле просто разово сходить на каждую из 19 страниц, чем городить таблицу
соответствий атрибутов.

### Принятое решение по хранению

**Пересмотрено**: иконки **хотлинкаются напрямую с `cdn.poedb.tw`** в `<img src="...">`,
без скачивания и без переразмещения файлов в своём репозитории. Причины смены решения
(изначально предлагалось скачивать и коммитить локально, см. историю раздела):
- Проще в разработке и поддержке — не нужен отдельный шаг скачивания/коммита ассетов при
  каждом обновлении списка скиллов/восхождений.
- Авторские права — иконки являются датамайн-ассетами игры GGG; прямая ссылка на сторонний
  CDN (просмотр чужого изображения по ссылке) не создаёт копию на своей стороне, в отличие
  от скачивания и переразмещения файлов у себя.

Сайт в рантайме зависит от доступности `cdn.poedb.tw` — это признано некритичным: poedb —
такой же основной общепризнанный community-датабейс по Path of Exile, как и poe.ninja,
а не второстепенный ресурс, рисков по надёжности/доступности не закладываем.

### Уточнение: иконки скиллов — с официального CDN GGG, не с poedb

Проверено вживую (2026-09-20): у Grinding Gear Games есть собственный официальный CDN
`web.poecdn.com`, и иконки геммов на нём лежат по **тому же относительному пути**, что и
на зеркале poedb, только с расширением `.png` вместо `.webp`:

```
https://web.poecdn.com/image/Art/2DItems/Gems/{InternalCodeName}.png
```

Подтверждено на нескольких примерах, включая гемм со сложным внутренним именем
(`Artillery Ballista` → `MortarTotemBowSkillGem.png`). То есть workflow не меняется —
по-прежнему нужен скрейп `poedb.tw/us/Skill_Gems` для получения пары "отображаемое имя
скилла → InternalCodeName", но итоговая ссылка в JSON-таблице должна указывать на
`web.poecdn.com` (официальный первоисточник), а не на `cdn.poedb.tw` (чужое зеркало).

Для иконок **восхождений** такой же официальный путь на `web.poecdn.com` пока не найден
(путь `Art/2DArt/UIImages/Common/Icon{Attr}_{Name}` с официального CDN отдаёт 404) — для них
пока оставляем ссылки на зеркало `cdn.poedb.tw` как и раньше. Если позже найдётся официальный
путь и для восхождений — обновить аналогично.

### Итог: `data/icons.json` собран

Готова статичная таблица `{ skills: {имя → URL}, ascendancies: {имя → URL} }` под все имена
из вкладки "Умения и классы" (раздел 7) — без какого-либо скрейпера в составе сайта или
CI: файл собран один раз и закоммичен как обычные данные, как и договаривались.

- **Скиллы**: 158 из 160 — ссылки на `web.poecdn.com` (официальный CDN). Не нашлись:
  `Dark Pact`, `Magma Orb` — на сводной странице poedb их вообще нет (возможно, устаревшие/
  переработанные версии скиллов), для них в JSON стоит `null`.
- **Восхождения**: 18 из 19 — ссылки на `cdn.poedb.tw` (путь `UIImages/Common`, начиная с
  `Icon{АтрибутнаяПара}_{Имя}.webp`; для Scion — общий `IconStrDexInt.webp`, у неё нет
  отдельной ascendancy-иконки). Не нашлась: `Raider` — у самого poedb на страницу класса
  Ranger ссылка на "Raider" ведёт на не относящуюся к делу страницу ("Raider (Ascendant
  passive)", это другой игровой объект с тем же именем) — `null` в JSON.

Важное наблюдение по надёжности `cdn.poedb.tw`: при тестировании (много быстрых
последовательных запросов подряд) сайт за Cloudflare начал отдавать **403** на прямые
запросы без Referer, хотя сами файлы существуют и в норме отдаются с кодом 200 — похоже
на защиту от ботов/скрейпинга, а не на постоянное ограничение по Referer. Для обычного
браузерного трафика с реальной страницы риск ниже, чем у моих повторных автоматизированных
запросов, но стоит иметь в виду как потенциальный источник изредка "не прогрузившихся"
иконок восхождений в проде.

Три нерешённых позиции (`Dark Pact`, `Magma Orb`, `Raider`) — на усмотрение донабрать
вручную позже (например, через poewiki.net как альтернативный источник) либо оставить как
есть: сайт должен уметь показать плейсхолдер, если URL иконки — `null`.

По-прежнему нужен: один разовый (или периодический, при обновлении справочника скиллов/
восхождений) скрейп `poedb.tw` — не для скачивания файлов, а для построения и обновления
JSON-таблицы соответствия "название скилла/восхождения → URL иконки на `cdn.poedb.tw`",
которая коммитится в репозиторий как обычные текстовые данные (не изображения).

## 10. Поведение зоны превью — референс "песочные часы"

**Принято**: зона превью "толпы" (раздел 5/6) — это чёрная область, разделённая по аналогии с
песочными часами на верхнюю и нижнюю часть:
- **Верх** — шарики игроков, которым ещё не присвоено восхождение/скилл (состояние "А"),
  слегка покачиваются на месте, как песчинки в верхней колбе до высыпания.
- Когда игроку выпадает комбинация — его шарик **перемещается сверху вниз** (по аналогии с
  падением песчинки через горлышко часов) и оказывается в нижней части зоны.
- **Низ** — шарики уже разыгранных игроков (состояние "Б"), там движение **чуть активнее**,
  чем в верхней части (не просто лёгкое покачивание) — на них уже отображаются иконки
  восхождения и скилла.
